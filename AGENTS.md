# MineMods development contract (QA v2)

Applies to every agent and contributor using MngkLrd/gradlejar. The repository is shared: inspect the current main head and never force-push, overwrite unrelated changes, or publish untested binaries as verified.

## Non-negotiable contract and delivery verification

This is a binding development contract, not optional advice, a backlog, or a checklist to read only after the user notices a defect. It applies to every new task, continuation, hotfix, update, port, asset change, and release performed with this repository, including existing chats and agents working on older branches. The user does not need to repeat these rules.

- Before changing anything, read the current main AGENTS.md and applicable project instructions, QA guide and compatibility registry. Resolve the actual task scope, supported targets and required checks. Do not rely solely on remembered instructions or a stale branch copy. Follow the current contract while preserving concurrent unrelated work.
- Implement and execute all applicable mandatory requirements in the first delivery attempt. Do not selectively skip QA, texture/model review, dependency compatibility, packaging, or regression checks because a task is small, because the user did not repeat them, or because compilation succeeded. Use proportionate existing checks; do not expand into unrelated audits or mandatory heavy testing.
- Before a final delivery, inspect the actual changed files, final JAR metadata, required CI jobs and per-target evidence. Compare them against the applicable requirements. Verify that every required check has been executed and has a matching result, that known failures have been investigated, and that reported download links identify the actual artifacts. The existing machine-readable scenarios, QA JSON and CI evidence are sufficient; no extra prose checklist or duplicate test report is required.
- A failed, missing, skipped, pending, unsupported or inaccessible required check is not PASS. Fix in-scope defects and rerun affected checks before describing the product as complete or verified. If an actual tool/backend limitation remains, provide the best supported partial result and identify exactly what is unverified and why. Never convert an obstacle into an implicit exemption, weaken assertions, or declare the full product ready. A genuine non-applicable check must be distinguished from an unexecuted applicable check. Explicit owner-approved scope changes or exceptions must be recorded with their real limitations.
- Do not require the user to discover omitted checks or ask for a second audit. A later apology or admission is not a substitute for completing the original requirements. Correct omissions proactively when discovered. Keep engineering evidence in GitHub and the user-facing report compact.
- Treat this contract as the minimum required process, not a reason to block useful work: proceed with supported implementation and targeted verification, do not stop for ordinary technical decisions, and do not claim that a Markdown instruction alone provides technical enforcement. Preserve the existing release gates and do not bypass them via legacy or parallel workflows.

## Chat response and reporting standard

Mandatory for agents working with this repository: read the current AGENTS.md from main at the start of each new task or continuation before reporting work. Apply the following user-facing response format unless the user explicitly requests a different or more detailed format. Repository access alone does not guarantee that an agent has read the instructions.

- Default to concise, structured Russian-language replies when the user speaks Russian. Answer the question directly. Do not repeat the task, roadmap, architecture, process, file tree or previous updates unless specifically requested or necessary to resolve a problem.
- Progress updates: one short sentence or a compact list of actual changes. State feature names and outcomes, not implementation narration. Avoid multiple headings, decorative cards, diagrams, large tables, unnecessary graphs, filler, generic advice and repeated conclusions.
- Delivery: put the actual ZIP/JAR download link first when requested. Then provide one compact list with every new or materially changed feature and every material fix, one line per entry. Group equivalent ports/variants where this does not hide differences. Omit empty categories.
- Gameplay QA: use one compact report/table only when useful, with actual targets passed/total, failed, and not run; actual executed assertion or declared-coverage counts only when the evidence supports them. Distinguish build, server gameplay, network player and graphical client evidence. Show the real CI/evidence link. A tiny status bar or similarly minimal visualization is optional; never duplicate the same data in another chart or paragraph.
- Always state unresolved bugs, failed/untested targets, missing features, limitations, and significant decisions or deviations. Include the first meaningful failure in one line and identify affected targets. Never sacrifice accuracy or completeness for brevity; report what is unknown rather than inventing counts. Distinguish committed code, CI in progress, verified results and published artifacts.
- Keep detailed diagnostics, full logs, code diffs and engineering evidence in GitHub; link them instead of pasting them into the chat. Expand only when requested, when debugging requires an exact fix, or when essential user instructions would otherwise be omitted. For a full project, include necessary build/run instructions compactly. Do not ask the user to carry out technical work the agent can perform.
- Suggested delivery shape (omit unused lines): download link; **Changes** (short bullets); **QA** (one compact status line/table and CI link); **Remaining issues** (short bullets or "none identified within tested scope"). No mandatory prose report or duplicate Markdown artifact. This communication rule does not replace executable QA requirements or reduce the actual scope of engineering or testing.

## Reference mod analysis and adaptation — mandatory

When the user names another mod, modpack, game or external implementation as a reference, follow [MOD-ADAPTATION.md](docs/development/MOD-ADAPTATION.md) before implementing. Determine whether the request concerns behavior, architecture, algorithm, content, visuals, interoperability or an explicitly authorized fork. Inspect the actual relevant upstream version, source/docs/observable behavior and license boundaries; distinguish verified findings from assumptions. Extract the requested design principle, compare it with our current mechanics and public APIs, then produce an independent, target-native implementation with justified improvements and executable positive/negative/regression tests. Do not copy entire subsystems, merely rename upstream classes, introduce unnecessary dependencies, redistribute unlicensed assets or claim code provenance without evidence. If actual reuse is requested, verify applicable permission and fulfill its conditions before copying; open repository access is not permission by itself. Preserve existing save IDs, world generation invariants and subsystem ownership; for WorldLogic, Core is the authoritative shared provider and addons consume its public API. If data/API are missing, specify the missing contract and coordinate with its owner rather than invent or duplicate it. Record source/version, selected principle, adaptation decisions, provenance and test IDs in a compact project-local reference note when implementing a nontrivial adaptation. Implement the authorized mechanics; do not end at a research report unless research was the requested task. No automatic porting or unrelated product changes.

## Ecosystem integration — scoped mandatory standard

Follow [ECOSYSTEM-INTEGRATION.md](docs/development/ECOSYSTEM-INTEGRATION.md) for all WorldLogic modules and other explicitly designated multi-mod ecosystems. Before changing a subsystem, inspect the actual peer contracts and active PRs, reuse authoritative capabilities, expose coherent relevant public operations with versioned semantics, maintain the project-local integration manifest, implement available relevant integrations and test affected module combinations. Coordinate missing capabilities directly through GitHub issues/PRs; avoid duplicate requests and do not require routine owner relay. Ownership is declared by each provider, not a fixed addon list. Standalone mods are not enrolled merely because they share this repository: no compulsory APIs, manifests, capability registry or ecosystem QA for them. Do not equate this development policy with implemented runtime discovery or automated CI enforcement. Preserve existing QA gates and target scope.

## Minecraft visual style — mandatory when creating or changing assets

Follow [common Visual QA](docs/art/VISUAL-QA.md), including its mandatory shared visual policy and original Blockbench style guide. Then use only the applicable art branch: [blocks and vegetation](docs/art/BLOCK-ART.md), [items and armor](docs/art/ITEM-ARMOR-ART.md), [mobs and animals](docs/art/MOB-ART.md), or [HUD and GUI](docs/art/UI-ART.md). Open the relevant material/role entry of [vanilla art atlas](docs/art/VANILLA-ART-ATLAS.md) and actual reference PNGs; use the current executable Art Review Lock. New/changed living-entity assets require mob-specific evidence in addition to original visual obligations. Do not read unrelated art branches or historical research by default. Review every changed asset and all applicable states, fix real defects, and distinguish structural, artistic and graphical client evidence. No reduction of existing QA or release requirements.

## Development scope — product first, ports at the end

- Default to one active Minecraft version and one loader: the pair specified by the user or already established for the current development thread. If none is established, choose a reasonable single baseline and state it. The standard eleven-target matrix is a release/porting option, not the default development scope.
- During prototype, MVP, alpha, beta, RC, feature, balance, visual and bug-fix iterations, implement and test the active target only unless the user explicitly requests multiple targets. Do not proactively generate, update, audit, compile or test ports for other Minecraft versions/loaders on every iteration. Do not run full-matrix dispatches merely because historical ports exist. Do not ask the user to reconfirm the established target on each iteration.
- Preserve portable design and reusable assets when practical, without premature abstraction, speculative API compatibility work or changes to existing off-scope ports. Previously published ports remain untouched; they do not automatically become the same product revision as the active development target.
- Keep the active development cohort explicit in its profile and executable QA assignment. For a new single-target project, set qa.release_targets to that target. For an existing multi-target release cohort, preserve the declared complete-release contract: use a distinct development revision/profile/cohort when necessary, rather than silently shrinking or bypassing the existing release gate. Scope changes must not turn a partial build into an advertised full release.
- Run the real applicable QA on the active target and report the scope. Other Minecraft/loader pairs outside the current task are out of scope, not failed tests or missing required checks. Unavoidable CI invalidation of already enrolled consumers of changed shared inputs is different from authorizing new ports; do not disable those checks or mutate shared tooling just to suppress them. Prefer target-local changes during development.
- Porting is a separate, final production stage after the core product is ready and the user requests or authorizes it. At that stage, the porting agent adapts APIs, resources, dependencies and loader metadata, maintains behavior parity, and runs all required checks independently on each requested target before complete JAR-only packaging. If the user explicitly requests eleven versions or another multi-target set up front, honor that scope from the start.
- Loader compatibility within a single Minecraft/loader pair still follows the minimum justified runtime requirement below. Do not confuse supporting older builds of the same loader with porting to different Minecraft versions or loader families.

## Loader compatibility — minimum justified runtime requirement

Keep Minecraft version, build-tool versions, loader API compilation version, installed QA loader version, and declared player-facing runtime dependency range distinct. The exact `qa.loader_version` pin is for reproducible CI, not an instruction to require that exact loader build from players.

- Within the intended Minecraft/loader pair, preserve the broadest genuinely compatible stable loader range. Default to the existing proven minimum and the compatibility registry baseline, not the latest available loader. Do not raise a minimum or add an exact/latest-only runtime restriction merely because that is the version available in CI, the build environment, a template or a previous agent's project.
- Inspect actual packaged metadata (`fabric.mod.json`, `META-INF/mods.toml`, `META-INF/neoforge.mods.toml`), Gradle dependency configuration and any runtime version guards. Keep loader dependencies as appropriate compatible ranges (Fabric predicates; Forge/NeoForge version ranges and language-provider requirements). Avoid exact pins or unjustified upper bounds in distributed mod metadata. Keep genuine Minecraft, Java, API and dependency constraints intact; do not promise untested loader builds or incompatible Minecraft versions.
- Compile against a suitable compatible API baseline when practical. Raise a minimum only when a required API, dependency, known compatibility defect or explicit owner requirement makes it necessary. Prefer a simple compatible implementation over an unnecessary loader upgrade; never lower a minimum by editing metadata alone when the code requires a newer API.
- Validate the exact final JAR on the chosen minimum supported runtime loader (use the actual pinned `qa.loader_version` for that check, or record separate evidence if build/test versions differ). A successful build or test on a newer loader does not establish a lower minimum. Preserve existing evidenced compatibility on updates; when changing loader/API requirements, verify the affected minimum and a relevant newer compatible build where useful. No exhaustive testing of every intermediate patch is required.
- Report the actual minimum tested loader and any necessary restriction briefly. If the true minimum cannot be established, distinguish a conservative tested range from an unverified broader range; do not silently lock to the latest or invent compatibility. Do not modify the central registry or unrelated ports just to make a local project pass.

## Unified mod naming and versioning — mandatory

Follow [MOD-NAMING.md](docs/development/MOD-NAMING.md) for all mods, cores, addons and ports from their next versioned delivery. Use one stable public name: `series_addon` (core: `series_core`) or `modname` for standalone products. Product version is exactly three nonnegative integers `MAJOR.MINOR.PATCH`: major release generation, major feature/content update within that generation, and patch/smaller update. Keep Minecraft and loader separate. Do not create new product versions with RC, alpha, beta, dev, build labels or a fourth numeric component; record development status and build provenance separately. Preserve the actual product version in Gradle, metadata, profile, dependencies and release notes. Do not silently invent a historical RC-to-version mapping or reset a published version.

Player-facing JAR names use `series_addon_A.B.C_MC_LOADER.jar` or `modname_A.B.C_MC_LOADER.jar`, e.g. `worldlogic_trauma_1.2.3_1.21.1_neoforge.jar`. Lowercase ASCII, underscores as separators, numeric product version before exact Minecraft version. Preserve existing registry IDs, namespaces, Java packages, slugs and dependency identities unless explicitly authorized to migrate them. Current Build Hub's older canonical filenames still govern its exact QA and package checks: use the checksum-preserving delivery helper after eligibility verification until canonical packaging migration is separately tested. Never rename input artifacts or bypass existing QA. No historical mass renaming or forced port builds.

## Mandatory for new projects
1. Define Minecraft, loader, Java, Gradle, mappings and real dependencies. Use `tools/qa/compatibility.json` as the reference matrix; it contains tested/pinned baseline choices, not a universal promise of compatibility.
2. Add `build-profile.json` with `qa.mode`, exact `qa.loader_version` (CI runtime pin, not a player-facing exact version requirement), complete `qa.release_targets`, standard JAR name, and (for gameplay mods) a positive regression scenario under `tools/qa/scenarios/`. Client-only mods use mode client, not a dummy server.
3. Compile the real Gradle project. Validate the actual final JAR, metadata, class target, JSON and data-pack layout.
4. For gameplay mods, boot the official installed loader with the exact release JAR, run assertions against the world and retain logs. No development-server fallback may be called production-tested.
5. Convert each confirmed bug into a repeatable scenario or GameTest. Include positive and negative controls. Test each in-scope Minecraft/loader pair separately; the full matrix is required only for an authorized multi-target task or complete release.
6. Never bypass a failed QA gate, replace gameplay assertions with startup markers, fake outputs, or mark a client screenshot as a manual gameplay test.
7. Ship only eligible release JARs. Complete multi-port bundles require every declared target, exact checksums and no duplicate variants; ZIP contains JARs only. Report client status separately.
8. Existing legacy profiles are grandfathered temporarily to avoid interrupting ongoing development; label them legacy/static only and migrate before claiming runtime QA. Never add new exceptions without explicit owner approval.
9. Prefer shared tools over more hardcoded per-mod workflow jobs. Separate client and server code. Do not modify unrelated projects during a port.
10. Report actual CI run, first failure, test scope and limitations. A successful compile is not a successful gameplay test.

See `docs/qa/QA-V2.md`. The experimental client launcher is development-mode only; QA-5 requires manual client validation and the explicit checksum-bound manual client release workflow. Independent legacy workflows remain outside the v2 gate until migrated; do not use them to bypass the standard.

Use `tools/qa/port_audit.py` and the official named-server API diff before porting across 26.x. Treat findings as advisory, never blindly rewrite Java. Preserve crash incidents and regression evidence. Asset checking is part of enrolled JAR validation; protocol-client and performance diagnostics are separate from release approval.

When porting is explicitly authorized, prefer `python3 -m tools.qa.scaffold` and `tools.qa.port_plan`. Draft outputs are not working mods or release candidates; do not enroll until real mechanics and positive/negative regression tests are present. Prepare release notes from actual changes and QA evidence using `tools.qa.release_prep`.

Declare shared source roots in build-profile.json and Gradle. Shared inputs invalidate QA evidence. Use the migration catalog and explicit proposal tool for legacy enrollment; never claim unknown evidence is a confirmed bug or remove legacy exemptions without reviewed tests.

For bulk builds use @batch:slug1,slug2. Treat discovered Minecraft releases as candidates, not compatibility claims. Use required player_scenario for protocol-compatible gameplay ports; never label RCON-only tests as actual client actions. The standard eleven release targets remain unchanged; they are not automatically selected during single-target development. Extended targets require explicit review.

## Product QA assignment — mandatory for every new or updated mod

The agent responsible for a mod owns its product quality, not merely compilation. Before implementation, read this file and the relevant current QA guide and compatibility registry. Translate the user's requested behavior directly into complete machine-readable test scenarios, implement the mod, and run those scenarios automatically in GitHub Actions against the exact production JARs. The user must not have to write test instructions, inspect logs, operate the bot, or manually repeat technical tests on every port.

1. Maintain the QA assignment in machine-readable, executable form as part of the mod's source: JSON scenarios under `tools/qa/scenarios/`, wired to the mod's `build-profile.json` via `qa.scenario` and, where supported, `qa.player_scenario`, plus any real automated GameTests or client tests integrated into CI. These files are the assignment for GitHub Actions and the Minecraft test player; no separate prose task, Markdown assignment, Work agent, or human-written test plan is required. If the scenarios alone cannot express the coverage inventory or target exceptions, use a compact machine-readable JSON coverage manifest referencing executable assertion names; this manifest is not itself executable unless a runner explicitly supports it. Update the executable assignment on every feature addition, bug fix or port that changes expected behavior. See [assignment guide](docs/qa/QA-ASSIGNMENT-TEMPLATE.md). Create a stable test ID for every requested mechanic and every added or modified item, block, entity, recipe, effect, menu, interaction and other relevant content. Reconcile the inventory with actual registrations and resources so nothing is silently forgotten. Group equivalent variants only when every variant is enumerated and actually exercised.
2. For each test ID specify target versions/loaders, prerequisites, player mode, setup, exact player actions, independently observable expected outcomes, negative/boundary cases where applicable, and the executable scenario/GameTest reference. Include acquisition, use, consumption/durability, drops, persistence and interactions with other features where applicable. Test both intended behavior and behavior that must not happen. Do not treat a registered item, successful startup or a generic smoke test as proof of its functionality.
3. Author and maintain the real executable mod-specific server scenario and, on supported targets, the required network-player scenario (`qa.player_scenario`). GitHub Actions must be able to execute the assignment automatically using the existing QA runner; merely writing prose, a JSON description without executable steps, or a disconnected coverage manifest does not satisfy this requirement. Use the bot for actual player interactions wherever its capabilities permit; commands may prepare fixtures and independently observe the result, but must never perform the action under test or substitute for it. For unavailable bot actions or protocols, use an appropriate real server/GameTest or production-client test if available, clearly identify the backend and its limitations, and never claim bot coverage that did not occur. Client-only visuals, custom menus and rendering require appropriate client evidence; server assertions are not substitutes.
4. Cover the declared targets for the current task, including extended targets when requested, with equivalent behavioral expectations. Full release cohorts must still satisfy every declared target; see Development scope. Run applicable positive, negative, regression and lifecycle checks against the final JAR, retain evidence per target and per test ID, and compare port behavior. Where a test cannot be executed, record it as NOT_RUN or UNSUPPORTED with the precise reason, not PASS. A failed assertion or missing critical mechanic is a release blocker; untested required functionality must not be represented as fully verified or silently dropped from the assignment. Existing release-gate rules and client approval requirements still apply.
5. Investigate failures independently, distinguish mod defects from test/loader/infrastructure problems, fix in scope, and rerun the affected checks. Preserve confirmed regressions and update the assignment. Report concise, user-facing results: deliverable ZIP, supported targets, coverage and any remaining limitations. No invented pass counts or tests, no lowering assertions to obtain a green build, and no publishing a partial archive as complete.

## Generated recipe and visual QA tasks

Use the recipe inventory and candidate player scenarios emitted automatically by Build Hub for enrolled final JARs. Wire and execute applicable generated tests; never label a generated NOT_RUN scenario as passed. For unsupported serializers, tags or modded IDs, implement the appropriate actual test backend, or report the precise gap. Use Visual QA redraw-queue.json to review flagged assets against Blockbench and correct real defects, with at most one automatic redraw by default. These tasks are concise machine-readable inputs, not additional prose or manual user work.

## Enforceable QA evidence

Every enrolled server profile requires a nonempty machine-readable coverage array in its server scenario. Each entry has a stable ID, kind, subject and references to actual named assertions. Target applicability must be explicit. The common gate checks the references and executed PASS/FAIL/NOT_RUN results; supported protocol targets require a player scenario. Declared coverage is not proof of undiscovered functionality. Do not omit known mechanics or content to make a report green. Legacy exemptions remain separate, not verified QA. Do not force migration of already published legacy mods; use current infrastructure from the start on new mods and when applicable to updates. See the assignment guide.

## Stable shared infrastructure — scope boundary

Use Gradle JAR as the shared production toolchain. Routine mod agents should concentrate on the requested product: its code, assets, balance, compatibility, mod-specific QA assignment and executable tests. Do not routinely refactor, upgrade, or redesign the shared build system, QA runner, bot, workflows, compatibility registry, or other mods. Prefer existing capabilities. If a missing backend or shared defect blocks meaningful tests, document the exact limitation and reproducible evidence and continue with the best supported alternative where possible; propose a narrowly scoped infrastructure change separately. Agents have standing permission to fix evidenced blockers in their assigned mod, including unrequested technical bugs, compatibility, assets, balance defects consistent with the agreed design, and missing tests. A narrowly scoped shared fix is permitted when a reproducible shared defect genuinely blocks the product, no reasonable existing alternative exists, and the change is isolated in a separate branch/PR with regression tests and impact analysis. Do not merge a failing shared change or change unrelated products; major redesigns and loader/CI policy changes require a separate task. Avoid unrelated edits and do not force the user to manage technical details. Product completeness, actual gameplay evidence and stable delivery take priority over architectural novelty.
