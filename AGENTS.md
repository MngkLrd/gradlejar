# MineMods development contract (QA v2)

Applies to every agent and contributor using MngkLrd/gradlejar. The repository is shared: inspect the current main head and never force-push, overwrite unrelated changes, or publish untested binaries as verified.

## Chat response and reporting standard

Mandatory for agents working with this repository: read the current AGENTS.md from main at the start of each new task or continuation before reporting work. Apply the following user-facing response format unless the user explicitly requests a different or more detailed format. Repository access alone does not guarantee that an agent has read the instructions.

- Default to concise, structured Russian-language replies when the user speaks Russian. Answer the question directly. Do not repeat the task, roadmap, architecture, process, file tree or previous updates unless specifically requested or necessary to resolve a problem.
- Progress updates: one short sentence or a compact list of actual changes. State feature names and outcomes, not implementation narration. Avoid multiple headings, decorative cards, diagrams, large tables, unnecessary graphs, filler, generic advice and repeated conclusions.
- Delivery: put the actual ZIP/JAR download link first when requested. Then provide one compact list with every new or materially changed feature and every material fix, one line per entry. Group equivalent ports/variants where this does not hide differences. Omit empty categories.
- Gameplay QA: use one compact report/table only when useful, with actual targets passed/total, failed, and not run; actual executed assertion or declared-coverage counts only when the evidence supports them. Distinguish build, server gameplay, network player and graphical client evidence. Show the real CI/evidence link. A tiny status bar or similarly minimal visualization is optional; never duplicate the same data in another chart or paragraph.
- Always state unresolved bugs, failed/untested targets, missing features, limitations, and significant decisions or deviations. Include the first meaningful failure in one line and identify affected targets. Never sacrifice accuracy or completeness for brevity; report what is unknown rather than inventing counts. Distinguish committed code, CI in progress, verified results and published artifacts.
- Keep detailed diagnostics, full logs, code diffs and engineering evidence in GitHub; link them instead of pasting them into the chat. Expand only when requested, when debugging requires an exact fix, or when essential user instructions would otherwise be omitted. For a full project, include necessary build/run instructions compactly. Do not ask the user to carry out technical work the agent can perform.
- Suggested delivery shape (omit unused lines): download link; **Changes** (short bullets); **QA** (one compact status line/table and CI link); **Remaining issues** (short bullets or "none identified within tested scope"). No mandatory prose report or duplicate Markdown artifact. This communication rule does not replace executable QA requirements or reduce the actual scope of engineering or testing.

## Minecraft visual style — mandatory when creating or changing assets

The sole art-style authority for vanilla-style mods is the [Blockbench Minecraft Style Guide](https://blockbench.net/wiki/guides/minecraft-style-guide/). Read it before creating assets. Apply its principles, not an arbitrary procedural texture template. User-requested intentional non-vanilla styles are explicit exceptions only.

- Model: recognizable simplified silhouette; minimal purposeful elements; use planes and transparency for small details where appropriate; avoid unnecessary stair-step geometry, model/texture mixels and stretched UVs; preserve consistent texel scale, proportions and gameplay readability.
- Texture: deliberate connected clusters that describe shape and material, balanced hue/saturation/value steps, a restrained palette, no artificial smoothing, avoid banding, pillow/pancake shading, unnecessary dithering, noise and accidental jaggies. Do not copy one generic pattern across unrelated materials. A valid PNG or a fixed number of colors is not proof of art quality.
- Items: design at the vanilla 16x16 grid for ordinary drawn icons; establish silhouette, darker outline, midtone, highlight and shadow (top-left light), then refine the palette and material. Shade the outline; examine at native size. Use larger textures only when appropriate to the model/asset type and keep consistent texel density.
- Blocks: review a 3x3 tiled surface before detailed shading and again at the end; remove unintended repetition artifacts. Entities: plan UVs and shading with top/front generally lighter than bottom/back; design texture and geometry together. Distinguish genuine transparent materials, animation atlases and overlays from accidental AA.
- Use actual vanilla textures of comparable material/asset type as references, not a universal color or cluster quota. When the shared Visual QA tool is available, run it on new or changed assets and inspect its report and native-size/tiling previews; review warnings and correct real style defects. Use at most one automatic redraw pass by default, then review the result and continue with a targeted correction only if a material issue remains. Do not regenerate good art merely to optimize a numeric score.
- Review items in hand/inventory, blocks in-world, entities and animation in an actual client where supported and relevant. A PNG preview, protocol player or server test is not a rendered gameplay check. If client visual evidence is unavailable, state that briefly; do not claim visual certification. Keep normal asset checks fast: no full client startup for each texture, no mutation/stress tests for cosmetic changes, no mandatory manual user QA. Structural errors block a verified release; style heuristics are advisory and require artistic judgment.
- Report material visual fixes and outstanding issues concisely. Use existing tools; do not redesign the pipeline as part of routine mod work.

## Generated recipe and visual QA tasks

Use the recipe inventory and candidate player scenarios emitted automatically by Build Hub for enrolled final JARs. Wire and execute applicable generated tests; never label a generated NOT_RUN scenario as passed. For unsupported serializers, tags or modded IDs, implement the appropriate actual test backend, or report the precise gap. Use Visual QA redraw-queue.json to review flagged assets against Blockbench and correct real defects, with at most one automatic redraw by default. These tasks are concise machine-readable inputs, not additional prose or manual user work.

## Mandatory for new projects
1. Define Minecraft, loader, Java, Gradle, mappings and real dependencies. Use `tools/qa/compatibility.json` as the reference matrix; it contains tested/pinned baseline choices, not a universal promise of compatibility.
2. Add `build-profile.json` with `qa.mode`, exact `qa.loader_version`, complete `qa.release_targets`, standard JAR name, and (for gameplay mods) a positive regression scenario under `tools/qa/scenarios/`. Client-only mods use mode client, not a dummy server.
3. Compile the real Gradle project. Validate the actual final JAR, metadata, class target, JSON and data-pack layout.
4. For gameplay mods, boot the official installed loader with the exact release JAR, run assertions against the world and retain logs. No development-server fallback may be called production-tested.
5. Convert each confirmed bug into a repeatable scenario or GameTest. Include positive and negative controls. Test each supported Minecraft/loader pair separately.
6. Never bypass a failed QA gate, replace gameplay assertions with startup markers, fake outputs, or mark a client screenshot as a manual gameplay test.
7. Ship only eligible release JARs. Complete multi-port bundles require every declared target, exact checksums and no duplicate variants; ZIP contains JARs only. Report client status separately.
8. Existing legacy profiles are grandfathered temporarily to avoid interrupting ongoing development; label them legacy/static only and migrate before claiming runtime QA. Never add new exceptions without explicit owner approval.
9. Prefer shared tools over more hardcoded per-mod workflow jobs. Separate client and server code. Do not modify unrelated projects during a port.
10. Report actual CI run, first failure, test scope and limitations. A successful compile is not a successful gameplay test.

See `docs/QA-V2.md`. The experimental client launcher is development-mode only; QA-5 requires manual client validation and the explicit checksum-bound manual client release workflow. Independent legacy workflows remain outside the v2 gate until migrated; do not use them to bypass the standard.

Use `tools/qa/port_audit.py` and the official named-server API diff before porting across 26.x. Treat findings as advisory, never blindly rewrite Java. Preserve crash incidents and regression evidence. Asset checking is part of enrolled JAR validation; protocol-client and performance diagnostics are separate from release approval.

For new ports, prefer `python3 -m tools.qa.scaffold` and `tools.qa.port_plan`. Draft outputs are not working mods or release candidates; do not enroll until real mechanics and positive/negative regression tests are present. Prepare release notes from actual changes and QA evidence using `tools.qa.release_prep`.

Declare shared source roots in build-profile.json and Gradle. Shared inputs invalidate QA evidence. Use the migration catalog and explicit proposal tool for legacy enrollment; never claim unknown evidence is a confirmed bug or remove legacy exemptions without reviewed tests.

For bulk builds use @batch:slug1,slug2. Treat discovered Minecraft releases as candidates, not compatibility claims. Use required player_scenario for protocol-compatible gameplay ports; never label RCON-only tests as actual client actions. The standard eleven targets remain unchanged; extended targets require explicit review.

## Product QA assignment — mandatory for every new or updated mod

The agent responsible for a mod owns its product quality, not merely compilation. Before implementation, read this file and the relevant current QA guide and compatibility registry. Translate the user's requested behavior directly into complete machine-readable test scenarios, implement the mod, and run those scenarios automatically in GitHub Actions against the exact production JARs. The user must not have to write test instructions, inspect logs, operate the bot, or manually repeat technical tests on every port.

1. Maintain the QA assignment in machine-readable, executable form as part of the mod's source: JSON scenarios under `tools/qa/scenarios/`, wired to the mod's `build-profile.json` via `qa.scenario` and, where supported, `qa.player_scenario`, plus any real automated GameTests or client tests integrated into CI. These files are the assignment for GitHub Actions and the Minecraft test player; no separate prose task, Markdown assignment, Work agent, or human-written test plan is required. If the scenarios alone cannot express the coverage inventory or target exceptions, use a compact machine-readable JSON coverage manifest referencing executable assertion names; this manifest is not itself executable unless a runner explicitly supports it. Update the executable assignment on every feature addition, bug fix or port that changes expected behavior. See [assignment guide](docs/QA-ASSIGNMENT-TEMPLATE.md). Create a stable test ID for every requested mechanic and every added or modified item, block, entity, recipe, effect, menu, interaction and other relevant content. Reconcile the inventory with actual registrations and resources so nothing is silently forgotten. Group equivalent variants only when every variant is enumerated and actually exercised.
2. For each test ID specify target versions/loaders, prerequisites, player mode, setup, exact player actions, independently observable expected outcomes, negative/boundary cases where applicable, and the executable scenario/GameTest reference. Include acquisition, use, consumption/durability, drops, persistence and interactions with other features where applicable. Test both intended behavior and behavior that must not happen. Do not treat a registered item, successful startup or a generic smoke test as proof of its functionality.
3. Author and maintain the real executable mod-specific server scenario and, on supported targets, the required network-player scenario (`qa.player_scenario`). GitHub Actions must be able to execute the assignment automatically using the existing QA runner; merely writing prose, a JSON description without executable steps, or a disconnected coverage manifest does not satisfy this requirement. Use the bot for actual player interactions wherever its capabilities permit; commands may prepare fixtures and independently observe the result, but must never perform the action under test or substitute for it. For unavailable bot actions or protocols, use an appropriate real server/GameTest or production-client test if available, clearly identify the backend and its limitations, and never claim bot coverage that did not occur. Client-only visuals, custom menus and rendering require appropriate client evidence; server assertions are not substitutes.
4. Cover all declared release targets, including extended targets when requested, with equivalent behavioral expectations. Run applicable positive, negative, regression and lifecycle checks against the final JAR, retain evidence per target and per test ID, and compare port behavior. Where a test cannot be executed, record it as NOT_RUN or UNSUPPORTED with the precise reason, not PASS. A failed assertion or missing critical mechanic is a release blocker; untested required functionality must not be represented as fully verified or silently dropped from the assignment. Existing release-gate rules and client approval requirements still apply.
5. Investigate failures independently, distinguish mod defects from test/loader/infrastructure problems, fix in scope, and rerun the affected checks. Preserve confirmed regressions and update the assignment. Report concise, user-facing results: deliverable ZIP, supported targets, coverage and any remaining limitations. No invented pass counts or tests, no lowering assertions to obtain a green build, and no publishing a partial archive as complete.

## Stable shared infrastructure — scope boundary

Use Gradle JAR as the shared production toolchain. Routine mod agents should concentrate on the requested product: its code, assets, balance, compatibility, mod-specific QA assignment and executable tests. Do not routinely refactor, upgrade, or redesign the shared build system, QA runner, bot, workflows, compatibility registry, or other mods. Prefer existing capabilities. If a missing backend or shared defect blocks meaningful tests, document the exact limitation and reproducible evidence and continue with the best supported alternative where possible; propose a narrowly scoped infrastructure change separately. Only change shared infrastructure when specifically tasked or a necessary, reviewed fix is authorized; use an isolated branch and validate it without weakening release criteria. Avoid unrelated edits and do not force the user to manage technical details. Product completeness, actual gameplay evidence and stable delivery take priority over architectural novelty.
