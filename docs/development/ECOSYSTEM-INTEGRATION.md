# Ecosystem integration standard (v1)

Applies under [AGENTS.md](../../AGENTS.md) to multi-mod ecosystems automatically identified from owner intent and established project identity. WorldLogic is the first mandatory ecosystem. A request for an addon of our own global mod automatically enrolls the parent and addon; no separate opt-in is needed. Mere presence in GradleJAR, a similar name, shared tooling or ordinary compatibility does not enroll a standalone mod. Standalone mods do not need an API, integration manifest, registry or ecosystem QA unless their own requirements justify it. Existing ecosystem projects adopt this standard on their next relevant development change; do not mass-migrate unrelated products or ports.

## 0. Automatic classification

Before feature code, resolve the project's ecosystem from its existing integration manifest, established project documentation and the owner's task. If the owner describes a first-party addon of our global mod, reuse the parent's ecosystem ID or initialize a stable ID for the parent and its first-party addon. Persist the actual relationship in project-local integration.json (optional parent_module field). No separate request for an API, integration or enrollment is needed. Existing enrolled projects retain their stable ID. A standalone compatibility mod, optional dependency, naming prefix or shared repository alone is insufficient; do not enroll by fuzzy name matching. The developer interprets natural-language intent; CI reads the durable declaration and checks membership/target consistency, not arbitrary chat text. An unmerged parent is coordinated through its actual PR rather than invented in main.

## 1. Integration-first development

Before implementing or changing a subsystem:
1. Inspect current main instructions, the participating projects' actual source, public contracts, project-local manifests, relevant active development PR heads and open integration issues. Pin the inspected refs; an API promised in an issue is not an implemented API.
2. Identify existing owners of every relevant data set, state transition and event. Reuse an existing compatible capability before inventing another. Look at adjacent ecosystem mechanics, not only the feature's immediate caller.
3. Identify the meaningful data and operations the subsystem can expose to other modules now, including relevant queries, validated mutations, registration extensions and lifecycle events. Expose a coherent usable contract in the same feature change rather than exposing one getter per consumer request. Do not expose private internals, speculative mechanics, raw mutable collections or write access without a genuine use case.
4. Implement relevant integrations now when the provider contract is available and the requested product scope permits. Inspect the other direction as well: existing consumers may need to discover or react to the new capability. For missing contracts, coordinate directly through GitHub (section 5), rather than making the owner relay routine technical requirements.
5. Update the manifest, API documentation, executable QA and dependency declarations alongside implementation. A missing provider blocks only the dependent path, not unrelated work. Do not describe a proposed or unverified integration as complete.

## 2. Ownership and capability discovery

One authoritative owner per capability and data/state domain; extend a provider by its supported registration or extension contract rather than copying its tables, formulas, persistent state or mechanics. Shared ecosystem foundations belong to the designated shared provider (WorldLogic Core for WorldLogic); domain-specific logic belongs to the responsible addon. Ownership is discovered from actual contracts and explicit declarations, not a fixed global list of addon names. New addons declare their capabilities and dependencies without editing this standard. Resolve overlapping ownership with the affected providers before changing canonical data.

Use namespaced stable capability IDs (e.g. `example:material_properties`), independent contract versions/revisions, provider identity and availability. Prefer typed, narrow public contracts with stable DTOs/interfaces, documented units, reference states, optional/unknown semantics, valid inputs, errors, lifecycle/thread/side requirements, mutation permissions, and extensibility rules. Distinguish product version from API compatibility. Unknown is not zero or a fabricated physical value. Use explicit units (SI for physical quantities unless documented otherwise). Do not use legacy relative scores as SI values. Maintain compatible signatures and semantics; additive changes use compatible revisions, incompatible changes require a new contract version, migration notes and consumer coordination.

Discover exact capabilities and supported versions, not just mod presence. Prefer existing typed ecosystem discovery/registration facilities where implemented; otherwise use loader-appropriate optional bridges, with narrowly scoped cached reflection only where necessary. Check both availability and compatibility before use, isolate optional class loading and avoid cyclic hard dependencies. Required dependencies must be declared in loader metadata and fail clearly if missing or incompatible. Optional dependencies must preserve documented safe independent behavior, including absence, incompatible version, unknown data and runtime failure; log actionable diagnostics once or at a bounded rate. Do not silently duplicate authoritative data or side effects as a fallback. Mutations/events have explicit ownership, ordering, idempotency or duplicate prevention where relevant; never charge the same action twice. Respect server authority and existing persistence, protection and permission contracts.

A common runtime capability registry is recommended when an ecosystem has a demonstrated need. Its implementation belongs to that ecosystem's shared provider, not to GradleJAR globally. Do not require a new registry to use working existing public APIs, or claim that a registry exists until it is implemented and tested.

## 3. Discoverable machine-readable contracts

Each participating target project maintains `integration.json` in its project directory, alongside `build-profile.json`. Use the [manifest example](integration-manifest.example.json) as the v1 shape. Empty arrays are valid when a module currently offers or consumes no public capability; do not manufacture APIs to fill the manifest. Each active project declares its ecosystem ID, module/loader identity, actual target, provided capabilities, consumed capabilities and integration tests. Paths are repository-relative; entries must describe real source and executable tests, or explicitly mark missing/planned contracts and link the existing issue. Do not include an invented provider, method, test or version range.

Discovery is by ecosystem ID and capability ID across matching target manifests, plus active PRs when the source has not merged yet. Project documentation provides precise semantics and public signatures; the manifest is the index, not a second API specification. Provided entries identify canonical domains, contract version, revision, public entrypoints and documentation. Consumed entries identify version requirements, optional/required behavior, status, fallback and relevant issue links. A consumer resolves to a compatible actual provider; planned/missing capabilities are not callable. Use stable IDs across ports while declaring only the current active target and actual implementation.

Keep manifests next to their owners rather than maintaining a hand-edited central catalogue that becomes stale. A generated catalogue/dependency graph and CI checks may later aggregate these files. Until an actual validator and discovery tool are implemented, inspect the manifests and source directly; the JSON file alone does not enforce correctness or perform runtime discovery.

## 4. Integration QA

Use existing [QA v2](../qa/QA-V2.md) and [executable assignment](../qa/QA-ASSIGNMENT-TEMPLATE.md) on the established target. Record actual artifact hashes and provider versions. For each changed capability and affected consumer, cover applicable cases:
- provider contract: real inputs, units, boundary cases, unknowns, registration/extension, version and lifecycle semantics;
- consumer alone, with compatible provider, without optional provider, and incompatible provider where meaningful;
- real gameplay with the exact production JARs of affected modules (not stubs alone), asserting both state changes and absence of duplicate effects, including persistence/network/client checks when relevant;
- consumer regression and compatibility of changed public contracts, with minimal affected module combinations; test the complete ecosystem for cross-system changes or ecosystem release when available.

Record stable test IDs and executable test references in manifests, not a parallel prose test assignment. A successful standalone build does not prove interoperability. Report absent dependencies, failed gates, skipped or unsupported backend tests explicitly; use NOT_RUN rather than PASS. Do not install unapproved artifacts as release evidence or bypass existing QA. If approved dependency artifacts or an integration backend are unavailable, record the exact blocker and proceed with independent supported checks.

Target automatic validation, capability-impact analysis and execution of affected integration scenarios when shared tooling supports them. Do not introduce full cross-product builds on every change, force ports, alter existing release gates or enroll standalone mods. Until automated orchestration exists, developers must identify impacted consumers and use the supported targeted QA facilities; do not claim automatic enforcement.

## 5. Direct developer coordination

When a needed contract is absent, first inspect existing issues/PRs to avoid duplicates. Open or update one GitHub issue in the shared repository addressed to the actual provider owner, with capability ID, concrete gameplay need, exact inputs/outputs/units, read/write/lifecycle semantics, affected consumers and target, compatibility expectations, fallback/blocker, and executable acceptance criteria. Link it from the consumer PR/manifest and provider PR when available. Bundle related needs into a coherent domain contract instead of requesting unrelated speculative methods or repeatedly asking for individual fields.

Provider owners check relevant outstanding requests at the start of each continuation, review related consumer source before extending the API, document delivered signatures/version/semantics and link their exact commit, QA evidence and artifacts in the issue. Consumer owners check the issue and actual provider source before resuming the integration. No routine human relay, no duplicate issues, no modifications to another owner's product without authorization; propose isolated provider fixes through the appropriate owner/PR. Escalate only real design conflicts, product-scope decisions or unresolved blockers. GitHub is the durable handoff; this process does not imply autonomous background communication between inactive agents.

## 6. Adoption and enforcement

WorldLogic projects follow this policy for new integration-related work once merged. Existing contracts and standalone fallbacks are retained until a compatible migration is implemented. No fixed addon list or mandatory new registry is imposed on future ecosystems; each chooses its own shared provider and target. The manifest convention is a documentation/data contract, not an already-installed CI gate. Implement the shared runtime discovery and automated manifest/impact QA separately with regression coverage and explicit scope, without changing unrelated mods.
