# First-party ecosystem — API-first standard (v2)

Applies under [AGENTS.md](../../AGENTS.md) to multi-mod ecosystems automatically identified from owner intent and established project identity. WorldLogic is the first mandatory ecosystem. The first request for a first-party addon of ANY of our own mods automatically promotes that original mod to the Core of its own ecosystem, and enrolls both Core and addon; no separate opt-in, explicit word Core or separate API task is needed. An addon for an external/third-party mod does not promote that mod or create our ecosystem. A standalone product with optional integration remains standalone. Mere presence in GradleJAR, a similar name, shared tooling or ordinary compatibility does not enroll a standalone mod. Standalone mods do not need an API, integration manifest, registry or ecosystem QA unless their own requirements justify it. Existing ecosystem projects adopt this standard on their next relevant development change; do not mass-migrate unrelated products or ports.

## 0. Automatic classification

Before feature code, resolve the project's ecosystem from its existing integration manifest, established project documentation and the owner's task. If the owner describes a first-party addon of our global mod, reuse the parent's ecosystem ID or initialize a stable ID for the parent and its first-party addon. Persist the relationship before feature code in both project-local schema-2 integration.json and build-profile.json ecosystem_membership. The parent becomes role core, its stable module ID is core_module; the addon becomes role addon and points parent_module/core_module to that root. Preserve the existing mod ID, namespace, save format and existing dependencies. Addons of existing first-party ecosystems reuse the same Core even if they extend another addon; sibling integrations are capability edges, not competing new cores. If the parent is not in the current branch, coordinate its real Core promotion in the parent owner's PR; do not fabricate it or claim complete integration. No separate request for an API, integration or enrollment is needed. Existing enrolled projects retain their stable ID. A standalone compatibility mod, optional dependency, naming prefix or shared repository alone is insufficient; do not enroll by fuzzy name matching. The developer interprets natural-language intent; CI reads the durable declaration and checks membership/target consistency, not arbitrary chat text. An unmerged parent is coordinated through its actual PR rather than invented in main.

## 1. API-first development — part of the feature, not a follow-up

Every first-party Core and addon exposes its actual useful domain functionality through its own typed, versioned public API in the same delivery as the feature. The internal implementation and external API call the same authoritative logic; never maintain separate behavior for API calls. Start with the complete coherent domain surface (query/snapshot, validated commands, events, extension points as appropriate) and its real peer interactions. A feature must not be delivered as complete if the useful domain API is deferred, implemented only as a stub, or merely promised in an issue. Purely private rendering, helper functions and internal implementation details need no artificial public method; document their scope in the feature inventory. This is not a request for speculative functions or universal mutable access.

For each new or changed domain, inspect the existing Core and relevant addon APIs and their source before writing feature code. Review the complete realistic interaction surface with peer owners in one pass, including the inverse direction, and bundle missing operations by domain rather than making a new API module for each scalar. Design extensible immutable DTOs/snapshots and semantic operations with documented units, lifecycle and capabilities. An API consumer should be able to query meaningful domain state, perform permitted actions, subscribe or register when relevant, and discover version/availability without reading private fields. Prefer a single public domain contract over a collection of ad-hoc getters. Do not invent future mechanics just to fill an API; compatible additions increment the contract revision.

Example design (not a claim about actual shipped methods): Trauma exposes a complete injury snapshot and validated injury/healing operations plus relevant events; Hydration consumes blood/fluid-loss information and exposes hydration state, intake and documented fluid-balance operations; TreeChopper queries material density and reports an impact through the existing injury contract. Each owner implements its own state once. Core hosts shared foundations and discovery, not every addon's gameplay implementation.

Before implementing or changing a subsystem:
1. Inspect current main instructions, the participating projects' actual source, public contracts, project-local manifests, relevant active development PR heads and open integration issues. Pin the inspected refs; an API promised in an issue is not an implemented API.
2. Identify existing owners of every relevant data set, state transition and event. Reuse an existing compatible capability before inventing another. Look at adjacent ecosystem mechanics, not only the feature's immediate caller.
3. Identify the meaningful data and operations the subsystem can expose to other modules now, including relevant queries, validated mutations, registration extensions and lifecycle events. Expose a coherent usable contract in the same feature change rather than exposing one getter per consumer request. Do not expose private internals, speculative mechanics, raw mutable collections or write access without a genuine use case.
4. Implement relevant integrations now when the provider contract is available and the requested product scope permits. Inspect the other direction as well: existing consumers may need to discover or react to the new capability. For missing contracts, coordinate directly through GitHub (section 5), rather than making the owner relay routine technical requirements.
5. Update the manifest, API documentation, executable QA and dependency declarations alongside implementation. A missing provider blocks only the dependent path, not unrelated work. Do not describe a proposed or unverified integration as complete.

## 2. Ownership and capability discovery

One authoritative owner per capability and data/state domain; extend a provider by its supported registration or extension contract rather than copying its tables, formulas, persistent state or mechanics. Shared ecosystem foundations belong to the designated shared provider (WorldLogic Core for WorldLogic); domain-specific logic belongs to the responsible addon. Ownership is discovered from actual contracts and explicit declarations, not a fixed global list of addon names. New addons declare their capabilities and dependencies without editing this standard. Resolve overlapping ownership with the affected providers before changing canonical data.

Use namespaced stable capability IDs (e.g. `example:material_properties`), independent contract versions/revisions, provider identity and availability. Prefer typed, narrow public contracts with stable DTOs/interfaces, documented units, reference states, optional/unknown semantics, valid inputs, errors, lifecycle/thread/side requirements, mutation permissions, and extensibility rules. Distinguish product version from API compatibility. Unknown is not zero or a fabricated physical value. Use explicit units (SI for physical quantities unless documented otherwise). Do not use legacy relative scores as SI values. Maintain compatible signatures and semantics; additive changes use compatible revisions, incompatible changes require a new contract version, migration notes and consumer coordination.

Discover exact capabilities and supported versions, not just mod presence. Prefer existing typed ecosystem discovery/registration facilities where implemented; otherwise use loader-appropriate optional bridges, with narrowly scoped cached reflection only where necessary. Check both availability and compatibility before use, isolate optional class loading and avoid cyclic hard dependencies. Required dependencies must be declared in loader metadata and fail clearly if missing or incompatible. Optional dependencies must preserve documented safe independent behavior, including absence, incompatible version, unknown data and runtime failure; log actionable diagnostics once or at a bounded rate. Do not silently duplicate authoritative data or side effects as a fallback. Mutations/events have explicit ownership, ordering, idempotency or duplicate prevention where relevant; never charge the same action twice. Respect server authority and existing persistence, protection and permission contracts.

Core must provide a stable capability discovery/registration contract for its own ecosystem, using an existing suitable typed mechanism if already implemented. Core cannot depend on concrete addon implementations. Keep interfaces and DTOs accessible without eagerly linking optional addon classes; use the loader's actual lifecycle, typed registration and compatibility checks. Expose read/command/event/extension roles as appropriate; no mandatory write access or invented state. During migration, preserve functioning public APIs and documented optional bridges until the Core registry is implemented and verified. Do not claim runtime discovery until actual Java implementation and compatible JAR integration tests exist. Each first-party addon keeps its own public domain API; do not move all addon logic into Core.

## 3. Discoverable machine-readable contracts

Each participating target project maintains `integration.json` in its project directory, alongside `build-profile.json`. Use the [schema-2 manifest example](integration-manifest.example.json) as the shape; all example paths, names and methods are illustrative, not actual modules. Schema 1 remains readable for already declared historical projects, but the next relevant development change must adopt schema 2. Schema 2 requires real provided capabilities, complete feature-to-capability mapping and implemented test references. Consumes may be empty only when no relevant cross-module need exists after reviewing peers; never fabricate APIs or dependencies. The Core's first promotion must expose actual shared capabilities in its own code. Each active project declares its ecosystem ID, module/loader identity, actual target, provided capabilities, consumed capabilities and integration tests. Paths are repository-relative; entries must describe real source and executable tests, or explicitly mark missing/planned contracts and link the existing issue. Do not include an invented provider, method, test or version range.

Discovery is by ecosystem ID and capability ID across matching target manifests, plus active PRs when the source has not merged yet. Project documentation provides precise semantics and public signatures; the manifest is the index, not a second API specification. Provided entries identify canonical domains (stable lowercase IDs within the ecosystem, e.g. material_properties, not arbitrary prose), contract version, revision, public entrypoints and existing repository-relative documentation. Consumed entries identify version requirements, optional/required behavior, status, fallback and relevant issue links. A consumer resolves to a compatible actual provider; planned/missing capabilities are not callable. Use stable IDs across ports while declaring only the current active target and actual implementation.

Keep manifests next to their owners rather than maintaining a hand-edited central catalogue that becomes stale. The shared static tool `python3 -m tools.qa.ecosystem` aggregates explicitly declared project manifests (including an enrolled root project). Run it locally; with `--base EXACT_COMMIT_SHA` it also computes affected declared consumers, preserving removed-provider edges. It validates schema, target, documented provider paths, implemented test-reference file existence, stable domain IDs, duplicate capability/domain ownership, parent hierarchy and required contract cycles. A required implemented capability absent or incompatible in the checkout is an error; if the provider is in another PR or external artifact, report the unresolved checkout and inspect that actual pinned artifact rather than claiming success. Optional absence and planned/missing contracts remain explicit warnings and not implemented. A compatible manifest match is only a declaration match, not actual Java ABI or runtime discovery. The tool does not read chat, infer membership from names or verify method bodies/test execution.

### Schema 2: executable API-first declaration

In build-profile.json use the following stable marker (replace all values with actual identity):

```json
{
  "ecosystem_membership": {
    "ecosystem": "example",
    "module": "example_provider",
    "role": "core",
    "core_module": "example_provider"
  }
}
```

Use the identical identity in integration.json. Core has no parent_module and identifies itself as core_module; addon includes parent_module equal to core_module. The graph identifies duplicate cores and unpromoted or absent Core declarations for the matching Minecraft/loader target. Third-party dependencies and compatibility addons do not add this marker solely because they depend on another mod.

For every provided capability, declare actual repository-relative source_paths and operations with unique id, kind (query, command, event or extension), entrypoint from the public entrypoints list, and meaningful semantics. The implementation and owner API documentation define exact signatures, units, validity, errors, lifecycle and compatibility. Each feature in features has a stable id, actual source_paths, provides and consumes arrays naming declared capability IDs, and concrete integration_review (which actual relevant peers/refs were inspected, what is reused or exposed and why). A feature with no provided public capability records no_public_surface_reason, explaining private implementation or consumer-only behavior. Every declared capability must map to a feature. Each provided or implemented consumed capability requires an implemented executable test reference; planned tests do not satisfy the gate. Sources must exist in the owner/shared roots and referenced docs/test files must exist. Keep the inventory current with actual registered gameplay, not a token placeholder feature.

Local check: `python3 -m tools.qa.ecosystem --check-project projects/your-project`. Build Hub runs the same scoped check for its selected project before Gradle. A missing manifest for an explicitly enrolled build profile or incomplete schema-2 declaration blocks that project; standalone projects are unaffected. This checks only static evidence and actual source/reference file existence, not Java signature correctness, inventory completeness, test execution or real integrations. Legacy v1 without a v2 marker remains readable; do not downgrade a v2 marker to bypass requirements. Full catalogue validation remains a separate command and graph preview remains advisory while independently developed provider branches are not all in the same checkout.

## 4. Integration QA

Use existing [QA v2](../qa/QA-V2.md) and [executable assignment](../qa/QA-ASSIGNMENT-TEMPLATE.md) on the established target. Record actual artifact hashes and provider versions. For each changed capability and affected consumer, cover applicable cases:
- provider contract: real inputs, units, boundary cases, unknowns, registration/extension, version and lifecycle semantics;
- consumer alone, with compatible provider, without optional provider, and incompatible provider where meaningful;
- real gameplay with the exact production JARs of affected modules (not stubs alone), asserting both state changes and absence of duplicate effects, including persistence/network/client checks when relevant;
- consumer regression and compatibility of changed public contracts, with minimal affected module combinations; test the complete ecosystem for cross-system changes or ecosystem release when available.

Record stable test IDs and executable test references in manifests, not a parallel prose test assignment. A successful standalone build does not prove interoperability. Report absent dependencies, failed gates, skipped or unsupported backend tests explicitly; use NOT_RUN rather than PASS. Do not install unapproved artifacts as release evidence or bypass existing QA. If approved dependency artifacts or an integration backend are unavailable, record the exact blocker and proceed with independent supported checks.

The existing Build Hub plan now prints an advisory ecosystem impact preview for relevant declared projects, including parent/consumer dependencies and prior-graph removal impact when the actual base is available. It does not expand the matrix, change existing outputs/gates or certify integration tests. A missing previous graph is explicit. The standalone catalogue validator exits nonzero for static graph errors; the Build Hub graph advisory report is deliberately nonblocking while existing projects adopt manifests and real artifact orchestration is absent. The separate scoped pre-Gradle project gate is mandatory for declared members; it validates actual local evidence without starting unrelated builds. Do not treat a green Build Hub run as contract QA. Target actual ABI validation and execution of affected integration scenarios when shared tooling supports them. Do not introduce full cross-product builds on every change, force ports, alter existing release gates or enroll standalone mods. Until automated orchestration exists, developers must identify impacted consumers and use the supported targeted QA facilities; do not claim automatic enforcement.

## 5. Direct developer coordination

When a needed contract is absent, first inspect existing issues/PRs to avoid duplicates. Open or update one GitHub issue in the shared repository addressed to the actual provider owner, with capability ID, concrete gameplay need, exact inputs/outputs/units, read/write/lifecycle semantics, affected consumers and target, compatibility expectations, fallback/blocker, and executable acceptance criteria. Link it from the consumer PR/manifest and provider PR when available. Bundle related needs into a coherent domain contract instead of requesting unrelated speculative methods or repeatedly asking for individual fields.

Provider owners check relevant outstanding requests at the start of each continuation, review related consumer source before extending the API, document delivered signatures/version/semantics and link their exact commit, QA evidence and artifacts in the issue. Consumer owners check the issue and actual provider source before resuming the integration. No routine human relay, no duplicate issues, no modifications to another owner's product without authorization; propose isolated provider fixes through the appropriate owner/PR. Escalate only real design conflicts, product-scope decisions or unresolved blockers. GitHub is the durable handoff; this process does not imply autonomous background communication between inactive agents.

## 6. Adoption and enforcement

WorldLogic projects follow this policy for new integration-related work once merged. Existing contracts and standalone fallbacks are retained until a compatible migration is implemented. No fixed addon list or mandatory new registry is imposed on future ecosystems; each chooses its own shared provider and target. The static validator, scoped API-first evidence gate and advisory plan preview are implemented. They are not a runtime registry or an automatic integration test gate. Only declared projects can be discovered; unmerged branches and undeclared existing modules are not magically indexed. Product agents must create truthful manifests on their next relevant change, using their actual source and pinned dependencies; do not bulk fabricate entries. Before promoting the planner to automatic builds, verify provider/consumer artifact hashes and loader/contract versions, compile/runtime classpath linkage, dependency order, affected same-target scenario execution and no duplicate side effects. Keep explicit manual target selection and existing release gates intact. Implement runtime discovery in Core separately; no global change to standalone mods.
