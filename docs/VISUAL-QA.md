# Visual QA and vanilla art standard

This is the canonical MineMods visual procedure under [AGENTS.md](../AGENTS.md). Use it before creating assets and when reviewing changed assets. It is not a claim that automated artistic judgment or graphical gameplay tests already exist.

## Source hierarchy

- Primary artistic reference: [Blockbench Minecraft Style Guide](https://blockbench.net/wiki/guides/minecraft-style-guide/). Read the original. It is community-maintained professional guidance, not a document published by Mojang.
- Supporting first-party art guidance: [Minecraft.net: Try the new Minecraft Textures](https://www.minecraft.net/en-us/article/try-new-minecraft-textures) (Jasper Boerstra interview) and [Caves & Cliffs developer Q&A](https://www.minecraft.net/en-us/article/caves---cliffs--part-i--dev-q-a). Consistent art direction, restrained geometry and pixel-art fundamentals reinforce our approach. Excessive anti-aliasing blurs the tiny sprites; a deliberate treatment in a comparable vanilla asset is more useful than a blanket alpha rule.
- Tool workflow: [Blockbench Overview & Tips](https://blockbench.net/wiki/guides/blockbench-overview-tips/) and Microsoft's official Minecraft Creator guides for [Blockbench](https://learn.microsoft.com/en-us/minecraft/creator/documents/blockbench) and [entity modeling and animation](https://learn.microsoft.com/en-us/minecraft/creator/documents/entitymodelingandanimation). The latter describe Bedrock: borrow modeling, UV, pivot and animation practices, not Bedrock schemas or APIs for Java mods.
- Technical reference: the actual target-version vanilla client assets and loader documentation, e.g. [NeoForge 1.21.1 models](https://docs.neoforged.net/docs/1.21.1/resources/client/models/) and [baked models/display contexts](https://docs.neoforged.net/docs/1.21.1/resources/client/models/bakedmodel/). Resolve model formats, item definitions, render types and resource paths according to the active Java Edition version. Do not copy a later-version schema unchanged.

The following review procedure is **our engineering standard**, derived from those references. It is not a Mojang certification or a reproduction of their internal guidelines.

## Mojang developer guidance: practical application

Jasper Boerstra's [June 2021 developer Q&A](https://www.minecraft.net/en-us/article/caves---cliffs--part-i--dev-q-a) emphasizes pixel-art fundamentals, pixel relationships and color theory. His [texture-update interview](https://www.minecraft.net/en-us/article/try-new-minecraft-textures) warns that excessive anti-aliasing blurs low-resolution art. Apply these as concrete reviews: use hue/value/saturation ramps, deliberate cluster placement, clear silhouettes, and readable material cues; do not generate noise or fake extra colors to satisfy metrics. Mojang's [Bedrock Copper Age changelog](https://www.minecraft.net/en-us/article/the-copper-age---minecraft--bedrock-edition-1-21-111-changelog) also explains the dye redesign in terms of visual consistency and distinguishable shapes for colorblind accessibility. Apply this general art principle to Java items and status icons: do not rely on hue alone to distinguish states. These are first-party statements; the detailed acceptance procedure and numerical warnings below are MineMods policy, not Mojang-mandated thresholds.

Additional first-party case studies and practical guides:
- [Meet the Phantom](https://www.minecraft.net/en-us/article/meet-phantom): Jasper describes intentionally testing a design beyond the existing style and using alpha on a body block to add detail. Review whether transparency communicates geometry; do not ban it universally or use it as an excuse for arbitrary holes.
- [Minecraft Maker Series: Making the Goblin Chef](https://www.minecraft.net/en-us/creator/article/minecraft-maker-series-episode-1--making-goblin-chef): the official introduction identifies Mojang artist Peter Sheff's three-part modeling, texturing and animation walkthrough, with attention to creative decisions such as colors and proportions. Use as an additional learning resource; the research has read the introduction but has not reviewed the full videos yet.
- [Minecraft Java snapshot 25w08a](https://www.minecraft.net/en-us/article/minecraft-snapshot-25w08a) documents a redesign of spawn eggs for readability/accessibility. This is a later-version case, not the 1.21.1 asset baseline. For distinct functional items and states, verify recognizable shapes and value contrast, not merely hue differences.
- [Vanilla art reference atlas](VANILLA-ART-ATLAS.md) and [research evidence](VANILLA-RESEARCH.md) contain actual verified 1.21.1 examples and known exceptions. Consult the corresponding material row when applicable, but still open the actual target assets. No numerical heuristic is an artistic pass or fail. [Real mod review examples](VANILLA-REAL-ART-REVIEW.md) show actual ground tiling and container-family defects, with concrete correction suggestions and limitations. Use these examples when relevant, without treating relative preference as release approval.

## Art production and review

### All assets

1. Choose a comparable vanilla reference from the target game before designing: same material, role, scale and asset type. If the exact target assets are unavailable, record the fallback version. Do not redistribute vanilla assets in the mod or reference reports unnecessarily.
2. Establish silhouette, proportions and a shared palette first; test the shape without detailed shading. Keep related variants recognizable and coherent. Give different materials distinct surface cues rather than reuse a generic noise/gradient algorithm.
3. At actual pixel size, paint meaningful contiguous areas, balance adjacent hue/value/saturation changes, and use selective contrast to describe volume and material. Review accidental jagged edges, repetitive diagonal bands, concentric shading, indiscriminate opposing highlights/shadows, redundant dithering and noise. A small isolated pixel can be intentional. Avoid automatic blur, filtered scaling, and mixed-resolution detail; do not equate every semitransparent pixel with an error.
4. Save lossless PNG and source model where applicable. Compare the rendered result next to vanilla equivalents; do not enlarge a low-detail design simply to add ornament. Preserve original editable sources if already available. Record asset-specific intentional deviations only where useful.

### Production sequence for substantial sprites (not just post-build lint)

Before painting a new item family, select and actually open one vanilla reference for shape/role and, when different, one for material. Examples: a glass bottle for a flask's neck and silhouette, a bucket for metal construction, copper ingot for copper color behavior, oxidized copper block for patina color relationships, leather armor for soft-material folds. These are comparison references, not shapes to copy or universal palettes. The active game version is preferred. Review a small representative group before generating many variants. No arbitrary procedural mass production of placeholder silhouettes.

1. Sketch a recognizable silhouette at native size, with a specific object construction (mouth, neck, shoulder, body, base, closure/strap where present). Shape must be understandable without a filename.
2. Establish the base tone and a darker, shaded outline. Blockbench's initial shadow and highlight establish the rough lighting; they are the starting pass, not necessarily the completed sprite.
3. Build the surface using adjacent groups of purposeful pixels. A cluster is a connected group of a single color for our measurements; neighboring clusters from a color ramp describe a plane change, turning surface, fold, recess, seam or highlight. A ramp and a cluster are different concepts. Add intermediary shades only where they clarify those transitions; avoid mechanical concentric rings, parallel bands, pillow/pancake shading and random flecks.
4. Work by material and light response: copper/metal has localized, relatively sharp highlights and darker turning planes; patina follows a believable surface region/edge, not an unexplained isolated gray mark. Cloth has broad soft folds, hems, and restrained contrast; leather has differently placed wear and seams; wood has grain aligned to construction; fired clay has matte curved planes, rim/base and restrained speckling when justified. These are MineMods art-review examples, not mandatory color recipes.
5. Inspect the actual PNG in a same-scale comparison with the selected vanilla reference(s) at 1x and nearest-neighbor enlargement. Use the local comparison tool below when available. Ask: what is this object without its name, what material is each part, where does the volume turn, and what do the clusters communicate? The reviewer must identify specific regions, not just report the count of colors/clusters.
6. If shape, material or light/shadow is unclear, stop before batch expansion. Rework the representative item, repeat the comparison, then produce coherent variants. For a known rejected family, do not accept another unchanged failure merely because the default one-redraw budget is spent; finish the targeted correction or report the remaining defect explicitly. Do not trigger unrelated Gradle builds between texture drafts.

For each changed family retain a short concrete comparison record with actual asset hash/path, reference game/version and IDs, and findings for silhouette, volume, material and cluster placement. Group truly equivalent assets only when every changed variant is inspected. A green lint result is not an art review. The comparator does not assign an artistic verdict, and no global minimum palette size or target cluster count is prescribed.

Local inspection without Minecraft or Gradle:
`python -m tools.qa.art_compare --minecraft 1.21.1 --candidate path/to/flask.png --reference item/glass_bottle --reference item/copper_ingot --reference block/oxidized_copper --out private-art-review`.
Optional `--client path/to/1.21.1.jar` reuses a local client after checking the official version SHA-1; otherwise the official client is fetched. Output includes a native/nearest-neighbor contact sheet and actual visible RGB frequencies/component counts per color with candidate and reference checksums. Inspect the sheet rather than comparing just the numbers. Keep vanilla comparison images local/private; never commit them, include them in releases or upload them as public artifacts. This tool is for static PNGs up to 128 pixels per side, not animated atlas interpretation, model rendering or art certification. If official references cannot be accessed, report the limitation and use a clearly identified comparable reference where available.

### Items and equipment

- Normal drawn item icons use the 16x16 canvas, with readable silhouette, controlled outline, top-left illumination and material-specific details. Inspect at native size, then with nearest-neighbor enlargement. Larger canvases, armor layers and 3D items are legitimate only when the design/reference warrants them; consistent effective texel density matters more than a universal PNG size.
- For clothing and armor icons, compare actual vanilla leather chestplate, leggings or comparable equipment and the intended material before drawing. Use the base silhouette and outline, then develop the color ramp and place fabric folds, collar, sleeve/cuff, hem or seams where recognizable at native size. Leather, linen and metal should not share identical highlights or the same flat fill. Check worn texture separately from the inventory icon. Preserve simple readable shapes; do not add meaningless detail to every pixel.
- A four-color palette is a review signal for a substantial item, not an automatic failure or a universal minimum. A base fill plus outline and two accents is insufficient if it does not depict material and form. Inspect the distribution and placement of shades, not just their number. Do not solve a flat texture by adding unused colors, random one-pixel flecks, noise or gradients.
- Check inventory/creative slots and tooltip readability, first- and third-person hands, dropped item and item frame where relevant; preserve vanilla-scale grip, angle and size. Compare left/right-hand transforms when supported. A flat generated item is acceptable for a sprite; an intended 3D item must actually render as 3D.
- Inspect layering, tint, transparency and special use states (e.g. charged, damaged, held at mouth). No clipping through the hand or invisible parts, missing-texture checkerboards or unexplained color differences between display contexts.

### Blocks and vegetation

- Work at block-scale 16 units per side; preserve texture scale on cut or rotated geometry. Preview a 3x3 tiled surface before detailed painting and after refinement, including top/side transitions and adjoining vanilla blocks. Check repeated knots, stripes, seams and directional light baked into tile edges.
- Minimize unnecessary cuboids and use purpose-built planes/cutouts for thin foliage, tendrils or small details. Check texel density, face orientation, transparent holes, tint, shading and silhouette from several angles. Check variants and neighbor states (connections, rotations, upper/lower plant halves, waterlogging when applicable); do not infer correct placement from a standalone PNG.
- For Terrain-style vegetation, compare species as a family in actual grass/forest/desert settings. They must have distinguishable silhouettes and coherent material/color treatment; verify biome tint, contact with ground, visibility through crossed planes and ordinary gameplay collision where relevant.

### Entities and animations

- Make body structure recognizable without texture; prefer economical cuboids and appropriate planar features. Set UVs and pivot hierarchy before animating. Match effective texel density on connected parts, preserve face orientation, check mirrored/asymmetric surfaces and seams; apply material shading consistently across body faces.
- Review actual pose, facing, scale, texture alignment, pivot rotation, hitbox interaction and attachment placement (saddle, equipment, held items). Test idle, locomotion and relevant attack/use/death or transition states, including areas revealed during motion. Do not certify animation from a single static pose.
- Non-grid geometry is allowed when supported by the asset format and justified by the visual target; avoid gratuitous tiny voxel detail or stretched faces.

### HUD and GUI

- Use the existing vanilla UI language for the specific target: font, icon grid, panel borders, spacing, slot geometry, hover/disabled state and readable contrast. Do not paste a generic web dashboard into Minecraft. Use the actual intended screen layout, not an image-generation mockup as evidence.
- Check normal and extreme states (empty/full, injured/healed, heat/cold, disabled, stacked effects, long tooltips). Check supported GUI scales, small/large window and relevant inventory/chat overlays; labels must not clip, overlap or cover vanilla HUD controls. Verify independent left/right limb markers and status/tooltip correspondence for anatomy UI, and synchronized values for climate/fatigue HUD when those features are affected.
- A vanilla texture reference is a visual comparator, not permission to override an unrelated interface. Keep state and display logic separate. Do not claim client UX verification from Java layout math or a successful server test alone.

## Non-negotiable material acceptance matrix (owner-confirmed examples)

The following are acceptance criteria, not suggestions. The owner confirmed the actual vanilla examples in comparative screenshots: central log bark, left spruce leaves, right log top, upper ground block, left leather armor icon, third and fourth saplings. Use the actual target vanilla PNGs to calibrate, not screenshot pixel counts or subjective complexity. The observations below describe visible differences; no universal quantitative palette quota follows from them.

| Material/profile | Required visual properties | Reject and redraw when |
| --- | --- | --- |
| Bark | Grain direction and varied features appropriate to the species; vertical ridges or horizontal lenticels/streaks; neighboring shades communicate structure | Mechanical uniform stripes, detached rectangles, indiscriminate reuse of an inappropriate or low-quality base |
| Log end | Growth rings with local micro-contrast, secondary clusters within broad rings, varied edges and textured bark boundary | Mechanical nested rings without material cues, flat single-color bands with no relevant variation, indiscriminate recoloring of a deficient base, solid frame without bark structure |
| Conifer foliage | Thin directed needle groups, branch-like structure, transparent openings that follow needles; restrained coherent palette | Large shapeless blobs, random holes, added complexity that erases needle structure; do not mistake intentional spruce needle diagonals for a flaw |
| Broadleaf foliage | Recognizable leaf groups with depth/overlap; transparency follows leaf silhouettes and natural gaps | Checkerboard or regular mesh unrelated to leaf geometry, big flat color blobs, generic green mass; do not merely recolor conifer foliage |
| Soil/ground | Varied connected aggregates, small neighboring hue/value changes, uneven boundaries and coherent tiled rhythm | Generic random pixels, repeating stamps, unbroken flat fields or excessive noise |
| Ore/inclusions | Host rock remains recognizable; inclusions have varied natural shapes, embedded edges, coherent light/material cues | Identical round stamps floating on the host rock, unrelated shadow rings or a recolor of the entire host texture |
| Clothing/armor | Clear silhouette and controlled contour; folds, collar, hem/cuff or seam where visible; material-specific shading | Flat outlined silhouette, arbitrary bright patches, large uniform fill with no fabric/leather/metal character |
| Sapling | Recognizable species silhouette, differentiated stem/branch hierarchy, attached foliage groups and purposeful small-scale shading | A stick with blobs, primitive disconnected branches, mechanically duplicated/recolored crowns |
| Vessel/flask | Readable neck, rim, shoulder and body; neighboring shades describe curved surface; distinct material treatment and physically motivated patina | Unreadable shape, one flat base fill with outline and arbitrary spots, identical metal/wood/clay shading |

All profiles must pass these common checks: recognizable silhouette or surface structure, cluster hierarchy (primary forms plus small purposeful secondary clusters), local micro-contrast where material requires it, coherent light and volume, material continuity, non-mechanical edge variation, identity relative to other variants, direct same-scale vanilla comparison. A simpler but faithful spruce texture is better than a more complex generic leaf texture. Broad color regions are allowed where the actual material/reference calls for them, not as a shortcut. No random added colors, dithering, or forced complexity to pass a heuristic. Intentional vanilla-like palette variants (e.g. dyes) may share geometry if the product explicitly calls for that; distinct species/materials must not be palette swaps unless justified by real comparators.

**Verified exception, not an exemption from review:** the official 1.21.1 oak, spruce, dark oak and acacia bark PNGs share the same color partition. Birch and jungle bark have different dominant direction and structure. Reusing an appropriate, well-developed structural archetype is valid when the actual comparable vanilla examples support it; require distinct material/role cues when needed for recognition or gameplay. Do not force unique pixel arrangements, extra colors or vertical grain for every wood. Record the comparator and why reuse is appropriate in variant_identity. Continue rejecting flat or unsuitable art and review every variant. See [R2 evidence](VANILLA-RESEARCH.md).

## Executable art review lock

Build Hub checks selected projects' tracked PNG textures under assets/*/textures/ against the fixed adoption tree (commit cb29b55). Only new/changed bytes relative to adoption require records; unchanged historical art is not migrated. The check runs before Gradle, including manual rebuilds and later code-only iterations of the same changed art. Unrelated projects are not blocked by another project's missing evidence. Deleted files need no review. Add the project-local `art-review.json` outside resources, with schema 1 and an assets object keyed by repository-relative PNG paths. Each entry must contain the actual PNG SHA-256, verdict PASS only after inspection, material_profile, reference IDs/versions/SHA-256 from inspected vanilla PNGs, a concrete comparison observation, and specific observations for every common and profile-specific criterion. See `tools/qa/art_review_lock.py` for the canonical executable criterion names. Use `art_compare` output for exact hashes; references may use a documented fallback game version when needed. Do not copy vanilla PNGs into the repo.

Valid profile names: `bark`, `log_end`, `conifer`, `broadleaf`, `soil`, `ore`, `clothing`, `sapling`, `vessel`, `other`. Choose the most specific applicable profile; other is for genuinely different materials, not an exemption. Common criterion keys: `silhouette`, `cluster_structure`, `micro_contrast`, `light_and_volume`, `material_continuity`, `edge_variation`, `variant_identity`, `vanilla_comparison`. Additional keys by profile:
- bark: `grain_direction`, `furrows_and_ridges`
- log_end: `growth_rings`, `ring_microstructure`, `bark_boundary`
- conifer: `needle_direction`, `structural_transparency`
- broadleaf: `leaf_groups`, `canopy_depth`, `structural_transparency`
- soil: `aggregate_structure`, `tile_rhythm`
- ore: `host_rock`, `mineral_inclusion`, `inclusion_light`
- clothing: `folds_and_seams`, `material_specific_shading`
- sapling: `branch_hierarchy`, `species_silhouette`, `foliage_attachment`
- vessel: `construction`, `surface_turn`, `material_specific_shading`
- other: `functional_material_cues`

A rejected or stale review, missing reference or missing criterion prevents compilation of the selected project. After changing pixels, inspect the revised image and update its hash and findings. Review records must describe concrete regions/relationships in the image; generic praise, copy-pasted observations across criteria or fabricated records are prohibited. The validator rejects duplicate observation strings but cannot determine artistic sincerity. The executable validator can check completeness and candidate hash, not the truth of aesthetic observations or reference provenance without separate source inspection. This lock does not certify rendering, check generated/untracked textures or non-PNGs, enforce external historical workflows, or configure GitHub branch protection. Those assets still require the existing visual review and final-JAR checks. No global numeric aesthetic pass rule. Do not weaken existing runtime/client release gates.

### Mandatory atlas application (R9)

Read the [vanilla art atlas](VANILLA-ART-ATLAS.md) before drawing and again during the actual review. Its machine-readable catalog is `tools/qa/research/vanilla-art-rules.json`: 57 inspected and official-client SHA-256-verified reference PNGs, 28 material/role rules with examples and limitations. The applicable rule is not optional, and numerical metrics do not replace the review.

Build Hub retains the original fixed-baseline review lock and adds a second fixed adoption tree `8e7d5b44a17360965ec0965874268d4112129d2d`. New or modified tracked PNGs relative to this second tree require an additional `atlas` object in the existing schema-1 per-asset review record. The original obligations remain for all assets enrolled by the earlier baseline; unchanged assets relative to R9 do not require retroactive new fields. Existing development branches must use current main tooling. No edits to old product branches or automatic fabrication of attestations.

Required `atlas` fields:
- `revision`: catalog revision (`r9`); `rule`: one compatible stable rule ID from the catalog.
- `reference`: namespaced ID (e.g. `minecraft:block/spruce_log_top`), `reference_minecraft`: exact matching version from one existing `references` row. For catalog rules the named comparator must belong to the rule and match its official 1.21.1 SHA-256. For other target versions also inspect the appropriate actual target reference when available, and state limits of the 1.21.1 artistic comparison; do not replace version-specific technical validation.
- `applied_pattern`: concrete description of what is visible in the candidate and how the actual reference informed its construction, palette or clusters.
- `reference_limit`: what should not be copied, a material-specific exception, or a justified difference from the comparator.
- `native_view`: actual observation at native size. `context_type`: `tile_3x3`, `icon_family`, `model_uv`, `placed_cutout`, `gui_state`, `animation_frames` or `other`; `context_view`: concrete observation in that preview. Soil/ore/bark/log-end profiles require a 3x3 tiled preview; use the relevant asset context otherwise. Static previews do not certify rendered gameplay.
- Only a genuinely uncovered `other` profile may use `rule: custom`; include `custom_reason` explaining why the catalog does not apply and `reference_source` identifying the actual vanilla source and verification method. The chosen reference must still match an actual `references` row. An applicable known comparator may not be routed through custom.

The validator checks rule/profile compatibility, reference membership/version and known official SHA-256 values, required distinct observations and context. It does not retrieve unlisted comparators in normal builds; their provenance and review observations remain attested. It cannot prove the agent actually saw the image or that its aesthetic judgment is correct. The catalog is verified against the official client in standalone research CI, not downloaded on every production build. A missing/stale/mismatched record blocks compilation for the affected project. The existing final-JAR, runtime and client gates remain unchanged. Current R9 verification: [research CI 46029695582](https://github.com/MngkLrd/gradlejar/actions/runs/46029695582) confirmed 57/57 catalogued PNG hashes against the official client and the expanded 240-pair experimental suite (280 pairs including the original pilot). See [research status](VANILLA-RESEARCH.md). These are not independent aesthetic approval results.

### Local preflight and working-branch rollout

Read current main, integrate its applicable QA tooling and catalog into the working branch without overwriting concurrent work, and verify the actual branch contains them before submitting changed textures. Main being updated does not automatically update existing branch CI. After committing the candidate PNGs and their truthful review records, run `python3 -m tools.qa.art_review_lock --projects '["projects/your-project"]' --check` from the repository root, substituting the actual project path (or `["."]` for the root project). Exit code 1 means evidence was blocked; the command prints each affected project and diagnostic. This local check evaluates committed-path changes and current bytes; it does not detect untracked files, replace final-JAR QA or certify aesthetics. CI mode remains unchanged and emits blocked projects through GITHUB_OUTPUT. No extra production job.

## Evidence and acceptance

| Evidence | What it establishes | What it cannot establish |
| --- | --- | --- |
| Packaged asset validation | Basic local references, resource integrity and supported geometry checks in the actual JAR | Art quality or actual renderer output |
| Fast Visual QA | Measurements, explicit model/PNG checks, previews and advisory review tasks | Accurate silhouette/material judgment, all inherited or code-generated models, in-game appearance |
| Aesthetic review | Actual asset/preview compared to a relevant vanilla reference using the above checklist | Successful runtime rendering or gameplay |
| Client review | Actual target client view of affected contexts, states and animations | Untested contexts or other versions/loaders |

Record PASS only for a review actually performed; use FAIL, NOT_RUN, UNSUPPORTED or N/A as appropriate. These are review outcomes, not new automated QA-level definitions. A structural defect under the existing applicable asset gate blocks a verified release; heuristic warnings require judgment and are not automatic aesthetic failures. A material visual defect should be corrected rather than ignored. If no suitable client is available, deliver honestly labeled development evidence and report exactly which views remain untested; existing release and manual client approval rules still apply. Group screenshots or animation checks by feature rather than launching a client for every PNG. No blocking subjective-score gate: the separate evidence lock checks required reviewed records, not an automatic taste score. No required manual user QA during ordinary development.

## Mandatory evidence for each changed asset

Inspect every new or changed asset, including those without lint warnings. Use `art-review-inventory.json` (all inspected textures/models, grouped by content hash), then `redraw-queue.json` for flagged candidates. Review actual native PNG/model or preview against a named vanilla asset and game version, with a specific judgment about shape, palette/material and shading/scale. If preview budget is exhausted, open the source asset directly. A zero-warning item is NOT_RUN until reviewed. Record separate structural lint, aesthetic review and real client rendering results in the normal delivery evidence; do not claim Visual QA PASS without stating the scope. A green workflow only means its executed checks succeeded. A reviewer can accept a genuinely simple icon with a reason, or reject a technically valid flat clothing sprite. Correct material flaws and review the revised hash. A screenshot of an asset thumbnail is not the original PNG or in-game evidence.

## Fast Visual QA implementation

The separate visual workflow runs on relevant texture/model/tool changes and does not start Minecraft or Gradle. It does not impose a new automatic release gate or mutate existing textures. The existing final-JAR asset gate remains active.

- Item/block/entity PNG: exact four-neighbor connected RGB clusters (ignore fully transparent pixels), isolated/small cluster fractions, palette count, equal-color neighbor fraction, adjacent HSV steps, partial alpha and alternating 2x2 patterns. Metrics and heuristic warnings are not aesthetic grades. Animated atlases/metadata are identified; frame-level style warnings and tiling omitted.
- Models: element counts, subpixel geometry and estimated unequal UV texel density for explicit JSON faces with resolvable local textures. Not inherited models, runtime/Blockbench meshes, material semantics or exact geometry certification.
- Real vanilla reference: selected item/block/entity textures from official 1.21.1 client, metadata and client SHA-1 verified, cached metrics only. Matching category/size ranges are contextual examples, not acceptance thresholds. The CI default is 1.21.1; select comparable actual-version references separately if needed. No redistribution of vanilla PNGs.
- Advisory low-complexity signals: for non-animated item textures with at least 32 visible pixels, four or fewer distinct visible RGB colors or a dominant color occupying at least 75% of those pixels prompts contextual review. These are deliberately conservative MineMods heuristics, not artistic pass/fail thresholds. Vanilla reference samples include armor icons. All inspected assets enter the review inventory even if no warning fires; automated aesthetic and client statuses remain NOT_RUN.
- Previews: native PNG, nearest-neighbor enlargement and 3x3 block tile for up to 32 unique textures. Review tiling visually. Transparent materials, thin elements, dithering and nonstandard sizes can be intentional.
- Structural errors: unreadable PNG, malformed model JSON, invalid explicit UV are job failures. Heuristic style warnings are advisory. Review the hash-bound redraw queue; make one targeted correction by default where a real flaw exists and recheck. Do not repaint good art to improve an arbitrary score.
- Full graphical gameplay validation, automatic visual regression, GUI semantic layout validation and animation analysis are not implemented by this linter; protocol bot has no renderer. No numerical threshold can certify vanilla art style.
- Run locally on changed assets: `python -m pip install Pillow==12.0.0`, `python -m tools.qa.visual_lint --paths path/to/texture.png path/to/model.json --out visual-qa`. Inspect final JAR if needed: `python -m tools.qa.visual_lint --jar build/libs/mod.jar --out visual-qa`. Generate reference with `python -m tools.qa.visual_lint --make-vanilla-reference 1.21.1 --out visual-reference.json` and pass `--reference visual-reference.json`.
- Report and previews are retained as MineMods-Visual-QA artifact. Review the actual changed images, not merely the green job status. See [QA guide](QA-V2.md) for release semantics.
