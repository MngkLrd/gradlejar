# Item and armor art standard — R11

Mandatory for item textures and equipment under [AGENTS.md](../AGENTS.md) and [Visual QA](VISUAL-QA.md). Active research target: Java Edition 1.21.1, NeoForge, Java 21, official mappings. Art principles carry across versions; asset paths, APIs and renderers must be verified for the actual target. No 1.21.2+ equipment-model JSON transplanted into 1.21.1.

## Evidence and classification

43 new actual PNG resource paths (31 item textures including one transparent overlay; 12 armor UV/overlay textures), retrieved from misode/mcmeta at 1.21.1-assets. Actual bytes decoded, local Git blob hashes checked against the archive entries, viewed at 1x and nearest-neighbor enlargement. The catalog SHA-256 values are subject to official-client verification in standalone research CI. Existing 57 reference paths remain; 100 total, not necessarily distinct visual designs. Actual 13 JSON models inspected from the same pinned archive: generated, handheld, wooden/iron axes, iron pickaxe/hoe/shovel, diamond sword, iron/leather chestplate, bow/bow_pulling_0 and shield. This is static art/model inspection, not gameplay renderer evidence.

Technical sources: [NeoForge 1.21.1 tools and armor](https://docs.neoforged.net/docs/1.21.1/items/tools/), [models](https://docs.neoforged.net/docs/1.21.1/resources/client/models/), [client item extensions 1.21.1](https://lexxie.dev/neoforge/1.21.1/net/neoforged/neoforge/client/extensions/common/IClientItemExtensions.html), [Mojang 1.21.2 equipment change notes](https://feedback.minecraft.net/hc/en-us/articles/31261174284557-Minecraft-Java-Edition-1-21-2-Bundles-of-Bravery). Read original [Blockbench style guide](https://blockbench.net/wiki/guides/minecraft-style-guide/) and actual target assets.

Classify by actual gameplay/render role, not just Java Item superclass or file name:
- Flat generated icon: ordinary usable or consumable object, tool, weapon, resource, container, medicine, book, etc. Classic flat source texture may generate thin geometry from alpha; do not confuse this with a custom cuboid or entity model.
- Stateful sprite/model: bow tension, cast fishing rod, charge/fill/use stages, tint/overlay, compass/clock, damage/state variants where actually implemented. These are not necessarily animated PNGs.
- Model-based item: shield, trident, block item, custom 3D tool or other renderer. Inspect geometry, UV and actual transforms; do not force a flat 16x16 silhouette or item/generated onto it.
- Worn armor/clothing: inventory representation and independent equipped model/UV layers. Other equipment such as elytra or horse armor needs its actual model and texture system, not a forced humanoid layout.
- Classify functional assets even when names differ from vanilla conventions. HUD icons, GUI widgets, block surfaces and entity UVs are separate categories.

## Flat usable items — mandatory production and review

At 16x16 (ordinary vanilla sprite baseline), establish silhouette/negative space before shading. Inspect at 1x against the actual family and at integer nearest-neighbor enlargement. Use meaningful primary and secondary clusters, coherent material ramps, localized highlights, shade edges by plane and role, avoid blurry scaling, excessive noise, rigid outline-plus-fill and arbitrary decorative pixels. Do not prescribe minimum palette count or visible area. A narrow functional object is not incomplete because much of its canvas is transparent. Preserve scale relative to other items; reserve consistent grip anchor, working-end direction and construction across a tool set. If an unusual item needs a custom shape or resolution, justify it using actual reference and model context.

| Family | Actual examples (1.21.1) | Construction and acceptance |
| --- | --- | --- |
| Axe | wooden/iron/diamond axe | 60 visible pixels each, 10 colors each. Broad chopping head with shaped cutting edge, joint and long grip. Head material has its own ramp; socket and face changes must communicate real construction. |
| Pickaxe | iron pickaxe (68 visible, 9 colors); wooden and diamond previously viewed | Long narrow curved/angled head, open gap under working head, clear socket. Don't turn it into axe or hoe. |
| Sword | wooden/diamond sword (84 visible each, 10/11 colors); iron previously viewed | Blade point, edge/spine, guard, grip and pommel distinguishable. Use a lengthwise shade ramp and controlled edge highlight, not random metallic speckles. |
| Hoe | wooden/iron hoe (51 visible, 7/8 colors) | Narrow single bent working end, handle and open space. Small silhouettes are legitimate; do not broaden them into a pickaxe. |
| Shovel | iron/diamond shovel (53 visible, 9 colors each) | Compact spade shape with face, shaded edge and neck. Keep handle/grip proportion and plausible socket. |
| Utility | flint and steel (85 visible, 12 colors), shears previously viewed | Function-specific separate parts and openings; sparks, cutting edges or fittings only where meaningful. Do not use a generic tool silhouette. |
| Stateful | bow + three pulling states; fishing rod + cast | Bow 70 visible at rest and 88 in each pulling sprite, with string and arrow shape changing; rod 67 to 54 visible as line/hook changes. Preserve grip, material and identity. Compare all states together, verify actual predicate/transition mapping. |
| Food/drink | carrot (96 visible, 10 colors), honey bottle (78 visible, 12 colors), potion | Plant/flesh/crust/liquid should have its own texture cues. Honey has a localized golden liquid volume inside the glass. Potion base is byte-identical to glass_bottle; final tinted contents depend on its actual model/layer registration. |

Shared archetype geometry is permitted for material progression when appropriate. For wooden versus iron versus diamond tools, consistent function is desirable; different material appearance is conveyed by ramps, local face/edge contrast and readable color relationships, not by adding needless shapes. At the same time, a new tool with different function must have an appropriate head/handle construction. The rule is not a one-color swap mandate or a unique-pixels mandate.

Implementation: in 1.21.1 classic sprite models reside in assets/<namespace>/models/item and reference textures/item using generated/handheld parent and layers. Inspect actual parent chain: the six inspected standard tool models use handheld; generated has front GUI lighting and default transforms; handheld inherits generated and provides left/right hand transforms. Bow uses generated plus its own display transforms and pulling predicates; shield uses builtin/entity and a blocking override, so do not paint it as a generic flat sprite. For custom item states, inspect actual model overrides/property registration and relevant target APIs. Confirm GUI, held first/third person both hands where meaningful, dropped and frame views, activation/charge states and stack/tint/durability behavior when applicable. Static comparison is not client PASS.

## Inventory armor and worn armor are different deliverables

### A. Inventory icon

Actual iron icons are 16x16 with 7 visible colors: helmet 78 visible pixels, chestplate 138, leggings 104, boots 88. The helmet has a strong dark opening, chestplate has recognizable collar and shoulders, leggings have a clear central split, boots are paired shapes with separate toes. The iron, diamond and chainmail chestplate icons have 138 visible pixels each and 7 colors. Chainmail depicts link texture with alternating gray clusters; it is not literally the worn transparent mask. Netherite chestplate has 138 visible pixels and 9 darker colors; it is readable through restrained planes and edge contrast rather than maximum brightness. Leather helmet/leggings/boots have 50/80/50 visible base pixels and grayscale ramps; compare the actual tinted composite. The leather chestplate overlay is fully transparent in the inspected vanilla file. It is intentional in this model's layered scheme, not proof of an absent chestplate. Do not judge overlay files by icon silhouette alone.

Draw each implemented equipment slot individually. Check head opening, neckline, waist/leg separation, feet/toes; match actual material thickness, plate/fabric construction and trim/closure cues to worn armor. In a full set compare all four icons at native size together. Keep icon identity consistent with equipped model without literally shrinking the UV atlas into an icon. Review actual tint, overlay, trim and glint combinations where supported. Iron/leather chestplate model JSONs use generated; both have trim_type overrides, leather also uses layer1 overlay. Do not paint pre-tinted leather or permanent trim over a dyeable base unless the design explicitly requires it.

### B. Equipped armor (actual 3D model)

For standard humanoid armor in 1.21.1, ArmorMaterial.Layer resolves the outer texture in assets/<namespace>/textures/models/armor/<material>_layer_1.png (helmet, chestplate, boots) and inner <material>_layer_2.png (leggings). Optional layer suffixes and dyeable layers follow the actual material registration. The 12 observed PNGs are 64x32; this is the vanilla humanoid atlas baseline, not a forced canvas size for custom geometry. The game places these texture regions onto 3D model faces; they are not inventory icons or arbitrary full rectangular paintings. Each actual head/torso/arm/leg face and mirrored mapping must be checked against the selected model. Do not guess left/right UV positions from a generic skin template. Keep intentional transparent unused regions; avoid UV bleeding and mismatched seam colors. Don't use 64x64 skin or newer equipment paths by accident.

| Material | Observed worn references | Required treatment |
| --- | --- | --- |
| Iron | layer_1: 648 visible, 7 colors; layer_2: 280, 6 | Plate edges and broad face light, align across actual cuboid face boundaries. |
| Diamond | 632/280 visible, 10/9 colors | Turquoise layered highlights and darker rims communicate faceted material, not random stripes. |
| Leather | base 660/280 visible, overlays 52/108 | Dyeable grayscale base, sparse warm seam/strap overlays; align both on actual UV, separate dye and non-dye layers. |
| Chainmail | 389/137 visible, 5/4 colors | Deliberate cutout link pattern; inspect underlying skin, seam continuity and correct render handling. Regular pattern is valid for this material. |
| Netherite | 699/272 visible, 9/9 colors | Dark material structure, restrained localized highlights and distinct shape coverage. Don't force iron's contrast onto it. |

Implement a registered armor item/material with correct slot/type, resources, item models and worn layers; verify all actual paths resolved. For custom bulky, layered or asymmetric armor geometry, use actual custom model and UV, client-only model registration/extensions and correct animation/pose following; standard vanilla ArmorItem rendering is sufficient for ordinary humanoid equipment. NeoForge 1.21.1 exposes client extensions for equipped models and per-layer tint. Do not instantiate client model/render classes on dedicated server. Later Minecraft versions use different equipment definitions and paths; consult target docs.

Before final acceptance, inspect actual 3D UV preview and actual game when supported: front/back/left/right, head/torso/arms/legs alignment; helmet on head (not inside face), chest and arms following animation, leg and boot separation; individual slots and complete set; regular/slim player model and relevant humanoids; standing, walking, sneaking and relevant poses; no missing texture, detached pieces, clipping or wrong layer. Test dye, overlay, trim and glint when implemented; normal mixed vanilla/custom armor and save/reload/equip/unequip. Do not present an offline mockup, flat UV sheet or server assertion as actual client rendering. If no real client is available, mark NOT_RUN or UNSUPPORTED with reason and obey existing release gate.

## R11 executable evidence

Existing schema-1 art-review records and r9 revision token remain. Use profile tool, stateful_item, functional_item, consumable, armor_icon, armor_icon_overlay or armor_uv as applicable, and matching atlas rule. Existing specific vessel/clothing/etc. profiles remain appropriate outside the new roles. If a truly uncovered item/armor subtype has no appropriate catalogued comparator (e.g. a novel complex device or custom geometry), use its specialized profile with the existing custom-reference evidence fields, not the generic other profile; known applicable references still require their catalogued rule. The canonical rules and required distinct criterion keys are in tools/qa/research/vanilla-art-rules.json and tools/qa/art_review_lock.py. New profiles require icon_family context for sprites or model_uv for worn armor. The comparison helper accepts models/armor reference IDs as well as item/block/entity.

For tracked PNGs added/changed since R11 adoption, in 1.21.1 projects the lock checks conventional tool and armor file naming against the appropriate profile. For an actually different semantic role using a conventional-looking name, supply a concrete non_equipment_reason tied to actual registration/model; do not use this as a bypass. Nonstandard names must still be reviewed according to actual role. For newly changed armor profiles the existing record must also contain equipment:
- slots: actual nonempty list of helmet, chestplate, leggings, boots (single for icon; outer cannot claim leggings, inner only leggings).
- binding: concrete description of actual item model/material/renderer linkage; client_status: PASS, NOT_RUN or UNSUPPORTED; client_evidence: actual evidence or explicit reason. A self-attested status is not automatically graphical QA.
- counterparts: one or more objects with slot, role (worn_uv for base icon; icon for worn atlas or inventory overlay), path (repo-relative PNG within the same project/declared shared roots) and sha256 of actual bytes. Every declared slot must have a valid counterpart. An intentionally reused known vanilla counterpart may instead use vanilla_reference (catalog ID without minecraft: prefix), its exact sha256 and concrete reuse_reason. For ordinary humanoid layer paths the lock checks inner/outer slot consistency. Shared atlas may cover only the actually implemented slots, not a fictitious full set.
- For overlay, link actual base icon and review composition. For worn layer, link relevant base icons. When changing a counterpart also refresh the corresponding changed review records. Custom geometry still requires actual registration/UV review, not inferred file naming.

This verifies evidence completeness, actual counterpart bytes and conventional naming/slot consistency. It cannot prove the actual item uses that resource, that UV faces match custom geometry, that all registered armor was discovered, or that a human/AI saw the equipped model. Those requirements remain in implementation and graphical QA. No forced migration of historical unchanged assets, no added production workflow job, no automatic art score. Use current main tooling and existing local preflight. Existing QA, final-JAR and renderer policies remain.
