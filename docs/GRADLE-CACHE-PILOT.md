# Gradle environment cache experiment

The current setup-gradle broad restore can load several GB of unrelated dependency and toolchain cache data. Measure before changing main Build Hub.

Pilot only: WorldLogic, Minecraft 1.21.1 / NeoForge 21.1.262 / Java 21 / Gradle 9.2.1 / ModDev 2.0.148. The existing production project and QA gate are untouched. The workflow seeds an isolated Gradle User Home cache once, then builds the same commit using current broad read-only policy and an exact-key restore of the seeded environment. Both run clean build with task-output caching disabled and normal JAR verification. A miss or incompatible toolchain fails the experiment, not the product. No cached product JARs, server worlds or release approvals are used. Timings separate setup, compile/verification and initial cache save cost; compare actual CI logs for compressed sizes and fallback keys. This is a compilation diagnostic, not server QA. No automatic product publication.

Pilot keys include run and attempt to avoid contamination by other experiments. This deliberately spends one initial cold build and two comparison builds only when the pilot itself is changed or manually dispatched. GitHub cache eviction/quotas still apply. The experiment is not a permanent cache warmer, and no all-version warming is enabled. If the measured warm result is beneficial, adopt a stable exact environment key derived from actual compile dependencies and loader/toolchain versions, with lazy population for active targets and controlled invalidation. Do not copy the per-run pilot key into production or discard the old fallback before measuring misses.
